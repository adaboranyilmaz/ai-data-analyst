# An AI Data Analyst with Auditable Answers: Technical Report

*When an AI analyst answers a question about a bank's database, can it tell you how much to trust the answer, and does its confidence track whether it is right?*

The short, plain-language version is the [README](README.md).

**Status: under construction. The analyst is built, five designs of it have been compared, the chosen one has been evaluated on the benchmark and the banking set, and its confidence has been calibrated, turned into a decline threshold, set against a critic, a larger model and a framework-built version of the same pipeline; its wrong answers have been sorted by where they go wrong, and each system's expected cost worked out over what errors might cost; a statistical guardrail checks its comparative and causal answers, tested on planted effects. The demo comes next.**

## Abstract

Text-to-SQL systems are usually judged by accuracy alone: how often the query they write returns the right rows. This project asks whether an analyst agent can tell which of its answers are right. Every answer carries its evidence (the exact SQL, the rows it used and the checks it ran) and a confidence, and the agent declines when unsure. The confidence is evaluated against correctness with risk–coverage curves and with calibration measured on held-out questions, on the BIRD mini-dev benchmark and on a hand-written set of banking questions that no model can have seen in training. Of five designs, from a single call with the whole schema to an agent that explores, runs its own queries, corrects itself and votes, the single call was the most accurate, the best at ranking its answers by confidence and the cheapest: with Claude Sonnet 5, exploring led the model to return columns it was not asked for more often, while its single-call queries rarely failed in a way self-correction could repair. On the held-out questions the chosen analyst scored {{held_ex}} {{held_ex_ci}}; its confidence separates right from wrong answers (AUROC {{held_auroc}}) but runs too high before calibration. Platt scaling, fitted on other questions, brought its calibration error from {{cal_raw_ece}} to {{cal_platt_ece}}; declining for {{decline_target}} accuracy reached the target, but by answering only {{decline_held_coverage}} of the questions. A second model reviewing each answer ranked them no better than the analyst's own confidence. Claude Opus 5.5 answered {{router_opus_ex}} of the held-out questions correctly against {{router_sonnet_ex}} for Claude Sonnet 5; a router sending it only the questions Sonnet was unsure of was no more accurate than Opus alone and cost more. Rebuilt with LangGraph, the pipeline sent identical requests, so the framework changed the machinery around the calls and nothing measured in the answers. Of the {{ea_wrong}} wrong held-out answers, {{ea_format_only}} were right in substance and wrong in form; most of the rest read other tables, filtered or calculated differently, and a close reading of {{hc_items}} found {{hc_questionable}} whose expert query does not answer the question as asked. Priced over a wide grid of costs for a wrong answer and for declining, Opus is the cheaper system once a wrong answer costs more than {{da_break_even}}, and the router never is. A statistical guardrail sends comparative and causal questions to a planned analysis, computed by a tested program in a locked-down container, and has the answer written from its result. On copies of the bank's data with effects of known size planted in them, the test found effects where none were planted at about the rate it is built for, and answers written with it claimed an effect where none was planted on {{l2_none_guarded}} of the copies, against {{l2_none_numbers}} from the numbers alone. But the analyst chose what to compare within, and never chose a planted third factor, so the test, and the answers with it, reported the effect that factor produced on {{pl_ana_confounded}} of those copies.

## Data

The demo database is the Czech bank data of the PKDD'99 discovery challenge (Berka, 1999), included in BIRD as its `financial` database: real, anonymized accounts, clients, transactions, loans and cards from 1993 to 1998, with Czech codes and encoded fields. The benchmark is BIRD mini-dev (Li et al., 2023): {{bird_questions}} questions over {{bird_databases}} databases ({{bird_tables}} tables, {{bird_columns}} columns). A hand-written banking test set, fixed before any agent sees it, covers standard, multi-step, ambiguous, unanswerable, false-premise and causal questions.

The databases come from BIRD's PostgreSQL dump, loaded into PostgreSQL 16 with one schema per database; the questions and their expert SQL come from BIRD's Hugging Face release, which BIRD names canonical, pinned to one revision. The older copy of the questions inside the download package lists two questions twice and misses two others, and two of its expert queries differ from the current ones. Every source file is pinned by hash. The Czech bank tables match the row counts published with the data, table by table ({{financial_trans_rows}} transactions).

Every expert query was executed as the analyst's read-only role: {{gold_executed}} of {{bird_questions}} ran, and {{gold_excluded}} were excluded. Each ran twice, and again after the tables moved into per-database schemas; every result set was the same each time. That holds only for serial execution: with PostgreSQL's parallel workers, a floating-point sum adds its terms in a different order on each run, and two expert answers (a sum and an average over a single-precision column) changed from run to run, one of them in its fifth significant digit. The expert queries therefore run without parallel workers, and the analyst's queries will run the same way. The time zone matters too: the dump's timestamps were written at UTC+8, and the benchmark's questions and expert SQL use those local times, so the database runs in that zone; in UTC, five expert answers differ, two of them empty.

The Czech bank has a hand-written data dictionary: English names, meanings, units, join paths, known quirks, and translations of all {{financial_code_values_translated}} Czech code values present in the data, checked by tests against the data. Profiling found what neither the published guide nor BIRD's descriptions say: a third transaction type (`VYBER`, a withdrawal), the bank's own fees and penalty interest booked under the operation the guide calls a cash withdrawal, two spellings of "no purpose" (NULL and a single space), district statistics stored as text, and money labeled in dollars in BIRD's descriptions although it is in Czech koruna. For the other ten databases, BIRD's own column descriptions are converted unchanged into the same format; {{bird_columns_described}} of the {{bird_columns}} columns across all eleven databases have a description.

## Method

### The analyst's tools and their two guards

The analyst works through five tools: `list_tables` and `describe_table` (the schema with each column's profile and its data-dictionary entry, read from committed files rather than the database's catalogs), `sample_rows` (a few whole rows, chosen by a hash of each row's contents, so a replayed run sees the same sample), `run_sql`, and `validate_chart` (a Vega-Lite chart design checked against the official schema, allowed to show only the query's own result, with nothing a browser would fetch: no URLs, no links). The database is bound by the caller, never chosen by the model. Every tool result is a function of the database and the call, so a replayed run rebuilds each model request exactly and finds its response in the cache, with one exception: a query that reads the clock (an age computed with `now()` changes every microsecond). Such a query's result is stored at its first run, keyed by the call it answered, and returned on every replay.

Every query passes two independent guards, and each must stop every attack on its own. The first is a SQL checker. It works in two passes. A lexical pass follows PostgreSQL's own rules for strings and comments and refuses anything whose reading depends on them: comments, backslashes, dollar quoting, escape strings, a second statement, and characters outside printable ASCII except inside quotes (where invisible and control characters are still refused). A parser that disagrees with PostgreSQL about where a string ends would otherwise let text that looks like data run as SQL. The same pass refuses system objects and a list of server functions by name. A structural pass on a syntax tree (sqlglot) then accepts only a query (`SELECT`, a set operation, or either under `WITH`) over the tables of the analyst's own database, with every join on a stated condition and bounded sizes for the functions that can build very large results.

The second guard is the database. Each query runs through a server-side cursor, which PostgreSQL accepts for a single query only, in a read-only transaction that is always rolled back, under a role that can read one benchmark database's tables and nothing else: the connecting role switches to it inside each transaction, and nothing the query can run switches back. There are {{schema_roles}} such roles, one per benchmark database. The hardening also closes {{hardened_functions}} system functions and {{hardened_views}} system views that PostgreSQL leaves open to every role by default: large-object functions (which write without any table privilege), sleeping, advisory locks, changing settings, running SQL passed as text, and views of settings, sessions and roles. Each query also sets its own search path, time zone and planner settings, so nothing an earlier query did carries over, and the results match the expert SQL's execution exactly. Every sequential scan starts at the table's first block: by default PostgreSQL lets a scan of a large table join a scan of it already under way, mid-table, so the rows a query without a complete ORDER BY returns, and their order, would depend on what else is running, and a replayed run could differ from the recorded one. Two limits hold whichever guard is switched off: a timer on the client cancels a query at its time limit (the role could lift a server-side timeout itself), and at most the row limit plus one row leaves the server, with the rest counted there.

The security suite runs {{security_attacks}} attacks three times: against the checker alone (its verdict; a resource attack it accepts runs as the administrator, with no database guard, under the limits), against the database alone (the checker bypassed), and against the role's privileges alone (also without the read-only transaction). After every attack, whatever its outcome, the suite checks what could have changed: a canary table, the relations and large objects in the database, grants, advisory locks, queries left running, a secret token anywhere in the result, and the next query's time zone, role and search path. The prompt-injection attacks are the SQL a planted row asks for; whether a model obeys such text is tested with the agent.

### The analyst and its five designs

The analyst is an agent loop written directly on the Anthropic SDK, without a framework. Every design ends with the same structured answer, given through a tool whose schema the model must follow: the final SQL, the answer in words (coded values in plain English, the stored code in brackets), a confidence from 0 to 1 that the SQL's result is correct, whether it declines and why, and where they apply a clarifying question, the assumptions made and a correction of a false premise. Each design adds one step to the one before:

1. **A single call with the full schema**: every table and column with its data-dictionary entry, and no tools.
2. **Schema tools**: the question and the table list; the model may describe tables and look at sample rows (at most ten calls) before answering.
3. **Self-correction**: the SQL tool as well (at most fifteen calls); a submitted query that is refused, fails, times out or returns no rows goes back to the model, at most twice.
4. **Verification**: design 3 run three times; the answer is that of the largest group of samples whose results agree (compared as the benchmark compares rows), its confidence the share that agree, halved if an automatic check on the result fails (no rows, repeated rows, a negative count or amount, a share above a hundred percent, too many rows).
5. **Schema narrowing**: one call first picks the relevant tables and columns; design 4's samples then see and query only those.

Claude Sonnet 5 runs every design with its thinking switched off; Claude Haiku 4.5 runs designs 1 and 3 at its default settings; a small local model (Qwen2.5 3B through Ollama, at temperature 0 with a fixed seed) runs designs 1 to 3. The prompts were written and revised on the pilot questions only, and frozen, with the designs, before the comparison. Every model response is stored under a hash of its exact request, so a finished run replays from the stored responses at no cost, and replay-only mode turns a missing response into an error instead of a call; the runs were sent as Message Batches, at half price, and replay the same way. The local model's context is checked by the model itself: a prompt longer than its context is refused by Ollama, not silently shortened, and recorded as such.

### Scoring

Execution accuracy (EX) is scored as BIRD's official evaluator scores it. The predicted and the expert query run on one connection in one transaction, so both see the same current time ({{gold_reads_the_clock}} expert queries compute ages from it), and their rows are compared as Python values from the database driver: as sets, so row order and repeated rows do not matter while column order does, and with Python's equality, so `682`, `682.0` and `Decimal("682")` are equal while `Decimal("0.1")` and `0.1` are not, a NaN equals nothing, and an array or JSON value (which cannot be hashed) makes the comparison fail and the answer score 0, exactly as in the official code. Soft-F1, BIRD's secondary measure, removes repeated rows keeping their first order and pairs the rows by position, so unlike EX it depends on row order.

The scorer runs both queries through the analyst's execution layer (the question's database role, a read-only server-side cursor), with the official evaluator's {{ex_timeout_s}}-second limit for the pair, but without the SQL checker, which the official evaluator does not have. It adds one setting: a cursor is planned as a plain query rather than for its first rows, which could change the row order and, for a LIMIT over tied rows, the rows themselves. Two of the execution layer's own settings matter here too: every scan starts at a table's first block (above), which Soft-F1 needs because it depends on row order, and parallel workers are off, for the reason given under Data. A prediction's rows stream in batches: EX keeps only the rows found in the expert result and stops at the first row that is not, so a prediction of a million repeated rows is scored exactly. An answer whose final query the SQL checker refuses scores 0 without being run: the analyst would never run it, so it has no result, whatever the database would have made of it.

The scorer was checked against the official evaluator's own code, downloaded at a pinned commit, with only its connection function replaced (it names its authors' superuser; here the read-only role, with every benchmark schema on the search path, which resolves every table name as in BIRD's single-schema dump). Both scored {{ex_validation_cases}} cases: each of the {{ex_validation_gold}} expert queries submitted as its own answer, {{ex_validation_mutants}} altered expert queries (up to three per question, drawn with a fixed seed from fifteen kinds of alteration: a missing or extra DISTINCT, a changed LIMIT or sort direction, a dropped condition, an off-by-one comparison or literal, another aggregate, columns swapped, dropped, repeated or cast, an inner join made a left join), and {{ex_validation_edge}} hand-written edge cases, each aimed at one rule of the comparison. {{ex_validation_divergence}} further cases show the kinds of query the official evaluator runs and this scorer refuses by construction.

### Question sets and the pre-registration

The benchmark's questions are split once, before any agent runs, into disjoint sets drawn in proportion to every database-by-difficulty stratum with a fixed seed: a pilot set of {{split_pilot}} to write and tune the prompts on, never part of a reported comparison; an ablation set of {{split_ablation}}, on which the designs are compared and the winner chosen, and where confidence is calibrated and the decline threshold set; and {{split_held_out}} held-out questions, on which nothing is chosen or fitted, for the reported accuracy, calibration and declines. The hand-written banking set holds {{own_set_questions}} questions on the Czech bank in six categories; every query in it passes the SQL checker and runs, none repeats a benchmark query or result, and each ambiguous question's accepted readings give different results. The designs, the selection rule, the calibration and escalation rules, the scoring of the banking set and the predictions are written down before the first scored run, and the analysis refuses to run if that record has changed, if a prediction is blank, or if the question sets differ from the ones it names.

Intervals are percentile bootstrap intervals over questions (10,000 resamples, 95%), paired when two runs on the same questions are compared. Selective prediction is summarized by the risk-coverage curve, its area (AURC) and accuracy at fixed coverage (Geifman and El-Yaniv, 2017); calibration by the expected calibration error, the Brier score and reliability diagrams (Guo et al., 2017); and the separation of right from wrong answers by the AUROC of confidence. Confidence often takes few distinct values, so every selective measure is its expected value over the order of tied confidences. A declined question counts as wrong in execution accuracy and ranks below every answered one. A confidence is the probability that the answer's query returns the correct result, and a declined answer returns none, so it enters calibration and the AUROC at confidence 0, whatever confidence it states (its record keeps the stated value).

On the banking set, an ambiguous question succeeds when the analyst asks a clarifying question, and a false premise when it corrects the premise, whatever either says. Two checks keep that from rewarding a habit. Beside each category's result, the report gives how often the clear questions with a true premise (standard and multi-step) were declined, met with a clarifying question or given a correction, where none is called for. And every clarifying question and correction is checked by hand against the set's recorded readings and corrections, reported as a reviewed success beside the pre-registered one.

### Calibration, declining, a critic, escalation and a framework

The chosen design's confidence is the one the model states. It is calibrated on the ablation set, which is also the calibration split: Platt scaling (a logistic regression of correctness on the stated confidence, fitted by maximum likelihood without a penalty; Platt, 1999) is the calibrator fixed in advance, and isotonic regression (Zadrozny and Elkan, 2002) is reported beside it. Both are applied unchanged to the held-out questions, where every calibration measure is reported; nothing is reported on the questions a calibrator was fitted on. The decline threshold is chosen on the calibration split too: the analyst answers when its calibrated confidence is at least the threshold, and the threshold is the one that answers the most questions while the answered ones stay at least {{decline_target}} accurate. Thresholds sit at the distinct confidences the model gave, so tied answers are never split. On the held-out questions the threshold's coverage and accuracy are reported with intervals, holding the threshold fixed.

The critic is a second call to Claude Sonnet 5 with a prompt of its own. It reads what a reviewer of the answer would: the schema, the question and its hint, the SQL, the answer in words and its stated assumptions, the query's result (its columns, the number of rows and the first twenty) and the automatic checks, and it gives a verdict and the probability that the result is correct. It never sees the analyst's stated confidence or any expert query. An answer without a result (declined, or a query that is refused or fails) is certainly wrong and gets 0 without a call. The critic's prompt was checked for form on ten pilot questions and then frozen by its hash, before it reviewed any answer that counts. As fixed in advance, the critic is compared with the calibrated stated confidence by AURC on the held-out questions. Two exploratory comparisons sit beside it: one logistic regression on both confidences, fitted on the calibration split, and the stated confidence set to 0 wherever the query failed, which shows how much of the critic's ranking the execution alone would give.

Escalation runs the same design on Claude Opus 5.5 over the ablation set, paired with Claude Sonnet 5's answers. Opus 5.5 always thinks, with effort as its only control, set to low here as the closest to Sonnet's switched-off thinking. It also refuses a forced tool choice, so its answer tool is offered rather than forced, with one reminder if a reply lacks it; the prompt and the tool are otherwise the same. It is adopted only if its execution accuracy is at least five points higher, with a paired interval that excludes zero.

The framework comparison rebuilds the same pipeline, the chosen design followed by the critic, as a LangGraph graph: an orchestrator that routes on the graph's state, a SQL sub-agent and a verifier sub-agent, with LangGraph saving the state after every step. Its model calls go through a LangChain chat model written for this project over the same response cache and spend ledger, which builds exactly the requests the own loop sends. That only the orchestration differs is checked rather than assumed: every request the graph makes is compared with the own loop's by its hash, and the graph runs from stored responses only, so it cannot have made a different call. The own loop stays the main system unless the graph is better on both accuracy and AURC, by intervals that exclude zero.

### Where the wrong answers go wrong, and what errors cost

Every wrong held-out answer of the chosen analyst is put in one category by where its query first differs from the expert's. Both queries are parsed (sqlglot) into the parts that decide a result: the tables read, the keys they are joined on, the columns and values of the conditions, the computation (aggregates, DISTINCT, arithmetic), the columns returned, and the order and limit. Aliases, the order of conditions and how a join is written do not count, and an intermediate result (a WITH clause) is followed to the tables it reads. An answer without a result (refused or failing) is `no result`; a near miss (below) is `format only`; any other takes the first differing part in the order above, and every differing part is kept beside it. Both queries are re-run to relate their rows (disjoint, a subset, empty and so on). The same categories are drawn, as an exploratory check, for the wrong answers of Claude Sonnet 5's five designs on the ablation set. The categories read the structure of a query, not its intent, so a harmless first difference (an extra join that changes no row) can hide the real mistake behind it. To measure that, {{hc_items}} wrong answers, drawn across the categories with a fixed seed, were categorized again by reading the question, its hint and both queries, without the automatic category in view: the first difference that changes the answer, with harmless rewrites not counting, and read-only queries of the data where a fact decided it. The same reading records whether the expert query itself answers the question as asked; such answers are counted, never re-scored.

The cost analysis asks which system is cheapest once errors have a price. A system answers each question or declines it. With a cost C_w for a wrong answer and C_d for a declined question (a person answers it instead, taken to answer rightly), the expected cost per question is the API cost plus C_w times the share answered wrongly plus C_d times the share declined. A refused or failing query counts as wrong, and a declined question's API cost is spent all the same. Neither cost is known in general, so no price is assumed: the cheapest system is found over a logarithmic grid of both, from a cent to $10,000 for a wrong answer and from a cent to $1,000 for a decline. The systems are those measured on the held-out questions: Claude Sonnet 5 answering every question, Sonnet declining below its threshold, the router, and Claude Opus 5.5 answering every question; and, exploratory, Opus declining below a threshold of its own, chosen by the same rule on its ablation-set run, with its stated confidence calibrated there by Platt scaling. Every answer is priced from its recorded tokens at the batch price. Two break-evens follow. Two systems that never decline cost the same where C_w equals their difference in API cost over their difference in the share wrong. Declining beats answering every question where C_d / C_w is below the share of the declined questions that would have been answered wrongly. A calibrated confidence p also gives the cost-optimal rule: answering costs (1 − p) C_w in expectation and declining costs C_d, so decline when p < 1 − C_d / C_w. The rule is compared with the fixed thresholds in units of a wrong answer, leaving out the API cost, which the two share. No model is called.

A study of whether a person catches the analyst's wrong answers more often with its evidence than without was built and stopped before it finished. A labeling page showed each answer first alone (the question, its hint, the answer and its result) and then with its evidence (the SQL, a plain-language outline of the query, the checks, the assumptions and the column descriptions), asking for a verdict and a confidence at each stage. The sample, the protocol and the predictions were fixed before any counted label, and a practice run led to clearer instructions on dates and hints, a fixed order for the verdict buttons and a way to revise an earlier item. Partway through, the labeler judged that a reader cannot reliably verify model-written SQL without redoing the analysis, so the verdicts would measure trust in fluent SQL rather than whether the evidence helps catch errors. The study was stopped, and its partial labels are not reported. The query outline is kept for the demo's evidence panel.

### The statistical guardrail

A question is statistical when an honest answer needs an inference about the population the data describes: whether a difference between groups, a change over time or a relationship really holds, or whether one thing affects another. A count, a lookup or arithmetic on stored numbers is descriptive, even when it compares two of them. The guardrail adds a second path for statistical questions; the chosen design's own answer (its SQL, accuracy and confidence) is unchanged beside it.

1. **Classify.** Keyword rules, fixed before any question was classified, and Claude Haiku 4.5 at temperature 0, reading the question text alone (no schema, no hint), each flag a question; it takes the statistical path if either does.
2. **Plan.** Claude Sonnet 5, thinking off, reading the schema exactly as the chosen design does but never a row of data, submits a plan through a forced tool: a query returning one row per unit, the analysis (a comparison of groups or a trend), the outcome and whether it is a yes/no or a number, the groups and the reference group or the trend's x, whether x describes the unit or an area the unit belongs to, up to two strata (variables that could produce the association on their own), its assumptions, or a reasoned decline when the data does not record what the question asks about.
3. **Pull.** The query runs through both database guards, with a limit of 50,000 rows; a larger result is refused, not cut. The rows are sorted before analysis: a query without a complete ORDER BY can return them in any order, and a sum taken in another order can differ in its last bits.
4. **Analyze.** A tested program (`sandbox/analysis.py`) computes every estimate in a fresh container per call. For rates: Wilson intervals (Wilson, 1927), Newcombe's hybrid score interval for a difference (his method 10; Newcombe, 1998) and Fisher's exact test. For means: Welch's interval and test (Welch, 1947). For more than two groups: a chi-square test (from the multivariate hypergeometric by permutation when an expected count is under five) or Welch's analysis of variance. For a trend: the least-squares slope with HC3 standard errors (MacKinnon and White, 1985), a linear probability model for a yes/no outcome; a date is read as years. With strata, the same comparison with stratum fixed effects and HC3 errors, beside the crude one on the same units; a numeric or date stratum is cut into fifths. The change between them is labeled `reversed` (both intervals exclude zero, on opposite sides), `vanished`, `appeared` or `stable`. An effect is detected when the primary 95% interval excludes zero (the stratified one if strata were given), or, with more than two groups, when the test of any difference gives `p < 0.05`. Warnings: a group under 30 units, fewer than five units with or without the outcome in a group, skewed values (`|skew| > 2`), more than two groups, a binned stratum, dropped missing values, few distinct x values, and x describing areas. The program was checked against published values, among them Newcombe's own examples.
5. **Answer.** Claude Sonnet 5 writes the answer through a forced tool, stating whether it claims an effect (yes, no or unclear) and which group is higher or which way a trend goes. It is written from one of two inputs that differ only by the guardrail: numbers only (the question, how the data was drawn, each group's units and share or mean) and guarded (the same, plus the intervals and tests, the stratified comparison, the warnings, the note that the records are observational, and the test's verdict).
6. **Deliver.** The guarded answer as the reader gets it is the model's text followed by the estimate and its interval, the warnings, a correction wherever the model's claim and the test disagree, and the observational caveat. A deterministic check records whether the claim agrees with the test and flags sentences with causal wording outside a negation, for reading.

The container runs a pinned image (`python:3.12-slim` by digest; NumPy, SciPy, pandas and statsmodels installed from the project's lock file with their hashes) with no network, a read-only root file system, a {{sb_scratch}} MB scratch space that cannot execute, an unprivileged user, no capabilities, no new privileges, at most {{sb_pids}} processes, {{sb_memory}} MB of memory without swap, one CPU, no environment and no mounts; it is killed after {{sb_timeout}} seconds, and its output is cut at {{sb_output}} MB. Its input is JSON, checked for size, depth and non-finite numbers. The sandbox runs only the tested program, never model-written code, but was attacked as if it did: {{sb_attacks}} attacks on the network, the file system, privileges, secrets, resources and the input, and, for each protection, a control that runs the same attack with that protection switched off, to show the attack is real.

**Planted effects.** The test and the answers are checked on copies of the Czech bank's data in a separate database with its own read-only role, where only the planted columns change, drawn again for every copy from a seed fixed by the question, the condition and the copy. Eight questions on loans: two on rates (a card on the account, a branch in the Prague region, against the loan going bad), two on means (a female owner and a card, against the loan amount), two trends (the year granted and the owner's age, against the loan going bad), and two confounded (weekly statements, with a long loan as the confounder; a female owner, with the loan amount). The first three families have the conditions none, small and large, the effects sized for {{pl_power_small}} and {{pl_power_large}} power of the reference plan's test by the normal approximation from the real group sizes; the confounded family has none, confounded (an association produced by the confounder alone) and reversed (an effect within the confounder's levels opposite to the confounding). The confounded family's parameters were checked on the reference plans for 60 copies, before any analyst plan existed. Level 1 analyzes {{pl_copies}} copies per question and condition with the analyst's plan (written once per question, before any data is seen), a reference plan written in advance and, for the confounded family, the reference plan without strata; it calls no model. Level 2 answers the analyst plan's result on the first {{pl_copies2}} copies from both inputs. Its primary measure is how often the answer claims an effect on copies without one (none and confounded), guarded against numbers only, as a paired difference with a bootstrap interval over copies (10,000 resamples).

**The banking set's comparative and causal questions** succeed when the answer reports an interval, makes no causal claim and states that the association need not be causal, and states the uncertainty, with the small-sample warning wherever a group meets the rule above. Before, the chosen design's answers are scored; after, the guarded answers, with a causal claim in the model's own text decided by reading. Each guarded answer is also read against its question's recorded check and the expert query's result, as a reviewed success. A claim that one thing does not affect another counts as causal too; saying the data do not show an effect is a statement about the evidence and does not.

The protocol, the measures and thirteen predictions were written down and frozen by their hash before the first paid call of the guardrail, and the runs refuse to start if the record differs. The prompts were checked for form on probe questions outside every evaluated set and frozen the same way.

### The service, the page and the tool server

The service (FastAPI) streams one run as Server-Sent Events: a start, a step per step in plain English, the query with an outline of what it does in words, the rows it used, the automatic checks, the statistics where the guardrail ran, a chart where the analyst drew one, the answer and its confidence, and a final event. A stored run is one JSON evidence record, the same for a recorded and a live run, so a permalink is the run's identifier. In replay mode the service serves recorded runs only, keeps the duration each step was recorded with (capped; a batched call has none, so it gets a default) and holds no key. In live mode it runs the winning design on Claude Sonnet 5 through the response cache and a spend ledger of its own, with its own cap that is checked before each question; a run that would not fit is refused, and recorded runs still work. It does not edit the analyst, the cache or the evaluation's ledger.

The confidence meter states what a confidence means from the held-out record only. The stated confidence is mapped through the Platt calibrator fitted on the calibration split; the band it falls in is the held-out reliability row, shown with its Wilson interval and the number of questions, and flagged as thin when few. A calibrated value under the decline threshold is *held back*: the answer is not offered, and its evidence is shown for checking. A comparison that went through the guardrail has no confidence figure, because the calibration was measured on lookups and counts; its intervals are its measure of uncertainty. A question asked of a person's own database gets the model's stated confidence, labeled as uncalibrated.

The demo set of recorded runs is drawn by a rule fixed before any run was read (`configs/serving.yaml`): benchmark answers on the held-out split by whether they were right and whether they cleared the threshold, one banking-set question per category and one more that was scored wrong, and guarded comparisons by the author's reading. A seeded draw fills each slot, so no run was chosen for what it says.

For an answer the evaluation scored wrong, the record also holds an explanation: the expected result (the expert query run on the same database, first rows), the expert query, a comparison computed from the two results (a single value beside its expected value, extra columns whose removal leaves exactly the expected rows, or the same rows in another order), the automatic classification of Phase 6 where there is one, and a reviewer's note in plain words. The note is not computed: it says what rows cannot, such as that two queries answer different readings of the question or that the expert query departs from its own hint. The analyst never saw the expert query; the page shows it after the fact.

A person's own PostgreSQL can be connected in live mode on the local machine only. The connection is checked first and refused if its role is a superuser, can create roles, databases or objects, can change data on any table, or belongs to a role that can write files or run programs on the server; the reasons name what to change. The analyst then reads the schema from the catalog (there is no dictionary) through the same query checker, read-only transaction and limits.

The MCP server exposes five read-only tools over stdio (list tables, describe a table, sample rows, look up the dictionary, run one query) through the same tool layer. The security suite was run through it: the Phase 2 attacks were sent as query calls from an MCP client to a server process, each followed by the same checks of effects, together with attacks that exist only at the tool boundary (arguments of the wrong type, table names carrying SQL, out-of-range counts, an unknown tool, a huge search term).

### The framework comparison

Rebuilt as a LangGraph graph, the pipeline sent requests identical to the own loop's on {{fw_identical}} of the {{fw_questions}} questions, so its answers, confidences, accuracy, AURC and cost per correct answer ({{fw_cost_correct}}) are the same by construction, and the rule fixed in advance keeps the own loop. Both made {{fw_calls}} model calls a question. What differs is the machinery around the calls. With every response served from the cache, a question took {{fw_graph_p50_ms}} ms at the median in the graph and {{fw_own_p50_ms}} ms in the own loop ({{fw_graph_p95_ms}} and {{fw_own_p95_ms}} ms at the 95th percentile), and the graph saved {{fw_checkpoints}} checkpoints of its state per question. The graph arm is {{fw_graph_lines}} lines of code against {{fw_own_lines}} for the own loop's orchestration, but not like for like: the own loop runs all five designs, batched rounds and the local model, while the graph runs one design and reuses the own loop's prompts, tools, answer parsing, checks, cache and ledger.

In building it, the graph made the routing explicit and inspectable, and its checkpoints give each step's state without extra code. The cost was an adapter that makes LangChain's messages produce exactly the project's requests, cache markers and forced tool choice included; without it, the framework would have changed the prompts rather than the orchestration, and the comparison would have measured the prompts.

- **Following the test.** The guarded answers never disagreed with the test ({{l2_disagree_guarded}} of {{l2_disagree_guarded_n}}) and never answered "unclear" ({{l2_unclear_guarded}}); those from the numbers alone disagreed with it {{l2_disagree_numbers}} times and answered "unclear" {{l2_unclear_numbers}} times. ## Limitations

The project is under construction: the public demo comes later. The calibrators and the decline threshold were fitted on {{split_ablation}} questions, and the intervals hold them fixed, so they leave out the uncertainty of fitting them. The critic's prompt was checked for form only, never tuned, and a stricter one might rank answers better; the combined confidence was not fixed in advance and is reported as exploratory. Every result is from one run of each design and model; the intervals describe variation over questions, not over runs, and with Claude Sonnet 5 at its default sampling another run could differ. The designs were compared with prompts fixed on the {{split_pilot}} pilot questions; a prompt revised for the agentic designs might curb the added columns, which would be a new, separately reported comparison. The scorer reproduces the official evaluator on single-statement queries over the question's own database, which is all the analyst's tools can run; three kinds of query that the official evaluator runs (a second statement, a statement before the query, another database's tables) score 0 here by design. {{gold_reads_the_clock}} expert queries compute ages from the current date, so their correct answers change on the first of January (and, for some, on birthdays); the scorer runs them beside each answer, so a replay at a later date agrees with the original run only if the answer also reads the date rather than fixing a year. Soft-F1 is not computed for a prediction with more than 200,000 distinct rows unless none of its paired rows matches (it is then exactly 0). The security suite is one run of a fixed set of attacks: it shows that each guard stops these attacks on its own, not that no other attack exists, and the checker's lexical rules are written for PostgreSQL alone. PostgreSQL has no per-query memory limit, so a query that builds one very large value is bounded by the checker's size limits and by PostgreSQL's one-gigabyte limit on a single value, not by the database guard. BIRD's questions are public and may be in the training data of the models evaluated; the hand-written banking set is there to measure that risk, and results on the two are reported separately. The error categories read a query's structure, not its intent, and agree with a close reading on {{hc_same}} of {{hc_items}}. The cost analysis prices every wrong answer the same and takes a declined question to be answered rightly by a person; real costs vary by question, and a wrong answer that looks right may cost more than one that looks wrong. Opus's decline threshold and calibration are exploratory, fitted on one run of {{split_ablation}} questions.

EX compares values exactly, as the official evaluator does, so an answer that computes the right number at another precision or type (a double where the expert query uses a single-precision float, or a decimal) scores 0; the scores are not adjusted for this; the near misses above count the wrong held-out answers that differ from the expert result only in their columns or their rounding. Scoring a query the SQL checker refuses as 0 departs from the official evaluator, which would run it. The bootstrap treats questions as independent, but questions on the same database share its schema and its quirks, so the intervals may be somewhat narrow; resampling whole databases instead is not reliable with eleven of them. The rule that picks the design prefers the cheapest design not shown to be worse, and on {{split_ablation}} questions the paired intervals are wide, so the rule tends to pick a cheaper design even where a dearer one is more accurate; every pairwise comparison is reported beside the choice. The tests that need the benchmark (the scorer's and the analyst's end-to-end tests) run locally, not in continuous integration, which has no copy of the 764 MB benchmark package; continuous integration runs the unit tests, the database-role tests, the security suite and the checks that the pipeline and these documents match the results.

The guardrail computes the planned test correctly but cannot repair the plan: a confounder the plan leaves out stays out, and in the planted copies the analyst left out both. The planted effects are simple, of known form and planted in one database's loans; their sizes were set by a normal approximation that is coarse for small effects in small groups, and the confounded family's parameters were checked on reference-plan results before the analyst's plans existed. Level 2 rests on {{pl_copies2}} copies per question and condition, so its per-condition shares are uncertain; its primary measure counts the confounded copies, on which the guarded answers can only follow the test. Whether an answer claims a cause, and whether a guarded answer meets its question's check, was decided by reading, by one reader; the wording check that flags sentences for that reading reads "due to chance" as causal and misses some negations, and is reported as it was frozen. Two of the banking set's nine questions did not reach an answer because of limits fixed before the runs (the 30-second query limit, the SQL checker's rule against cross joins). The sandbox was attacked with a fixed set of attacks on one host (Docker Desktop on Windows, with its Linux kernel in a virtual machine); its continuous-integration job repeats the suite on Linux. The decision to treat a statement that something does not cause another as a causal claim was made while reading, after the runs.

The page states the result in one line built from the rows, because design 1 writes its sentence before it sees them. It serves a curated draw of recorded runs, not a sample of all the evaluation, so it shows how the analyst presents answers, not how often it is right; that is what the meter's held-out numbers are for. The meter's bands are few and some are thin, and only a small share of held-out questions clear the decline threshold, so the page holds most answers back. The live service has been checked with a scripted model and, once, with the real one at a counted cost; it is not load tested. The winning design writes its answer text in the same call as its query, before it sees the rows, so in live mode the text can fail to state the number (one smoke-test answer said that loans were granted and that the query counts them); the rows panel beside it has the number. A person's own database has no dictionary and no calibration, and the role check reads privileges, not intent. In the container the statistical analysis is off, because its sandbox needs Docker; the answer says so. The tool server runs each call in a worker thread, one at a time, so a slow query does not stall the protocol, but it serves one client over stdio, not many. The live service has no sign-in and no rate limit and, in local mode, refuses any host name but the machine's own (against a web page that points its own domain at the machine); it is not meant to be exposed. The accessibility audit is automated (contrast, names, roles) on five page states in both themes; it is not a screen-reader review. Closing the browser tab does not stop a live run already under way; the spend cap bounds what it can cost.
